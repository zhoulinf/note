CH.0 导学：DSH 是什么，你将学到什么

DSH = DeepSeek Harness，是 DeepSeek 开源（MIT 协议）的 AI 编程智能体运行框架，仓库在 github.com/deepseek-ai/deepseek-harness。你现在正在使用的这个 Web GUI（http://127.0.0.1:3080）就是 DSH 的一个「表面（surface）」—— 用浏览器把框架能力呈现出来的方式。

0.1 一句话概括 DSH

DSH 是一个以 Cordis 插件框架为内核、用「配置补丁层（patch layer）」组合出不同运行形态（Web 界面、headless 命令行等）的智能体运行时。你可以把它理解为：

dsh CLI启动器
→
Profile运行形态
→
Bundle插件组合包
→
Cordis插件内核
→
插件/服务LLM·工具·会话·沙箱…

你写的每一行「提示词」、模型调用的每一个工具（pwsh、fs、goal、subagent、workflow……），背后都是一个 Cordis 插件在某个 Context 上注册的服务或工具。掌握了 Cordis，你就掌握了 DSH 的 90%。

第一部分 · 认识 DSH —— 先会用，再理解

这一部分不涉及深奥原理，目标是让你对 DSH 的整体形状有一个准确的直觉：它装在哪里、由什么组成、配置怎么流动。请动手跟着做。

CH.1 认识 DSH：组件全景与第一次启动

1.1 组件全景

DSH 由下面几个层次组成，从外到内：

层次是什么对应代码/目录
CLI 启动器dsh 命令：解析启动器自己的 flag，选择运行模式@deepseek-ai/dsh 的 lib/bin.js
Profile（运行形态）一个目录，声明由哪些 bundle 组合、以及用户自己的配置层$DSH_HOME/profiles/<name>/
Bundle（组合包）带 cordis.patch.yml 的插件集合包：dsh-base（核心）+ 各表面（web / headless）@deepseek-ai/dsh-base 等
Patch 层YAML 补丁：按 id 覆盖/插入「行（row）」，层层叠加cordis.patch.yml、--patch 文件
Cordis 内核依赖注入 + 插件生命周期 + 事件总线 + 服务注册表@deepseek-ai/cordis（v4 fork）
Loader把 patch 后的「行」变成真正运行的插件（Entry 树、热重载）@deepseek-ai/cordis-plugin-loader
插件/服务LLM 适配、会话、工具、沙箱、子代理、工作流、Web 服务器…@deepseek-ai/dsh-* 上百个包

1.2 本机安装形态

在 Windows 上，DSH 通常通过 npx @deepseek-ai/dsh 或全局安装运行。你机器上的真实情况：

  • DSH 代码：npm 缓存下的 _npx\…\node_modules\@deepseek-ai\（一个版本一份）。
  • 用户数据（$DSH_HOME）：C:\Users\zhoulinfeng\.dsh —— 这是所有配置与数据的家。
  • 桌面启动器：dsh-desktop\launch-dsh.ps1 —— 等价于执行 node …\dsh\lib\bin.js web --host 127.0.0.1 --port 3080，并自动打开浏览器。

CH.2 配置即代码：Profile / Bundle / Patch 三层模型

2.1 核心概念：行（Row / Entry）

在 DSH 里，一切可配置的插件实例都叫「行」。一行就是一个将要在 Cordis 里加载的插件条目，形如：

- id: tool-pwsh                    # 行的稳定 id(其他层靠它来覆盖)
  name: '@deepseek-ai/dsh-tool-pwsh'  # 要加载的插件包名
  config:                            # 传给插件的配置(会被 schemastery 校验)
    enableRunInBackground: true
  inject: [tools, shell, systemPrompt, shellEnv]   # 行级依赖注入(可选)
  disabled: false                    # 是否禁用(可选)

行的字段：id（唯一标识）、name（插件模块）、config（插件配置）、inject（加载前必须可用的服务）、group（嵌套分组）、disabled。

2.2 Patch 层：只写「差异」，不写「全量」

Bundle 和用户配置都是补丁（patch），不是最终配置。补丁引擎 applyEntryPatches（源码在 dsh-app-boot/lib/index.js）按顺序把补丁叠到空根上，规则只有三条：

  1. 按 id 覆盖：- id: xxx + 若干字段 = 找到已有行，整体替换这些字段（config 是整块替换，不是深合并！）。
  2. insert 插入：- insert: [ …新行… ] 在顶层（或某 group 内）追加新行；新行也立即进入索引，后续补丁可以再覆盖它。
  3. 找不到就警告跳过：patch 匹配不到目标 id 会 warn，不会报错。
# 覆盖已有行:把 web 的 system-prompt 整块换掉
- id: system-prompt
  config:
    persona: >-
      You are my personal coding agent.

# 禁用已有行
- id: skill-badge
  disabled: true

# 插入全新的行
- insert:
    - id: my-hello
      name: '@me/dsh-tool-hello'
      config:
        greeting: 你好
⚠️ 最容易踩的坑 「覆盖」是整块替换 config，不是合并。所以 web-app 补丁里 system-prompt 行要重新写全 persona，base 里 session-query-sqlite 行要重写 path 和 openAt 两个键 —— 源码注释里明说了「each row below restates every key it owns」。

2.3 补丁叠层的完整顺序

从 profile-boot 源码（composeProfile）可以拿到精确的叠加顺序：

① 空根
[]
→
② bundle 补丁
按 bundles 顺序
base → web-app
→
③ profile 用户层
profiles/web/cordis.patch.yml
→
④ 家目录用户层

→
⑤ --patch 覆盖层
按 argv 顺序
→
⑥ 遥测开关等

后层覆盖前层，同 id 后写胜出。dsh --dump-config 就是把这六步算完打印给你看。

2.4 !!js 表达式：配置里的 JavaScript

配置值可以嵌入 JS 表达式，语法是 YAML 的 !!js 标签。加载器把它变成 {__jsExpr: "…"}，在插件 fiber 激活时用 with (ctx) { eval(expr) } 求值（源码：cordis-plugin-loader/src/config/utils.ts）。这意味着表达式里可以直接用 ctx 上已注入的服务：

# 环境变量
- id: sandbox-policy
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()

# 平台判断
- id: tool-bash
  disabled: !!js process.platform === 'win32'     # Windows 上禁用 bash

# 读取已注入服务的值(web-app 的真实写法)
- id: webserver
  inject: [webStartup]
  config:
    host: !!js ctx.webStartup.host ?? '127.0.0.1'
    port: !!js ctx.webStartup.port ?? 3080

# boot 提供的路径助手
- id: session-persistence-jsonl
  config:
    root: !!js dshHomePath('sessions')

配合行级 inject: [webStartup]，DSH 实现了一个优雅的机制：命令行参数先由一个小插件解析并 provide 成服务，配置表达式再读取它 —— 于是「flag 驱动配置」不需要任何魔法。

2.5 settings.yaml：用户设置文档

与 patch 层不同，$DSH_HOME/settings.yaml 是「设置文档」：按命名空间组织、热重载（保存即生效）、由 Web 的 Settings/Models 页面读写。你机器上现在的真实内容：

# C:\Users\zhoulinfeng\.dsh\settings.yaml
ui-onboarding:
  welcomeNoticeVersion: 2026-08-13.1
ui-theme:
  preference: dark

模型配置（Models 页）会写入 llm-deepseek: / llm-pi-ai: 命名空间，覆盖 base 层对应适配器的默认值 —— 无需重启。凭证（API Key）则写在 .credentials.yaml，由凭证服务按需解析，不会注入到进程环境变量里。

2.6 本章小结

  • 配置 = 空根 + 若干补丁层；行是基本单位，id 是寻址键。
  • 覆盖是整块替换 config；插入用 insert:；禁用以 disabled: true。
  • 补丁顺序：bundles → profile 层 → 家目录层 → --patch → 系统补丁。
  • !!js 表达式让配置可以编程；settings.yaml 是热重载的用户设置文档。

CH.3 dsh CLI 深入：参数模型与插件管理

3.1 两段式参数模型（Launcher flags vs App flags）

这是 DSH CLI 最反直觉也最优雅的设计：启动器只解析自己的 flag，第一个识别不了的 token 之后全部原样交给 profile 里的应用（源码 dsh/lib/bin.js）。所以：

dsh --profile web --port 8080        # --port 是 web 应用的,不是启动器的
dsh --profile web --help             # 打印的是 web 应用的帮助
dsh --help                           # 启动器自己的帮助
dsh --profile headless "run the tests"   # 位置参数 = headless 应用的任务

应用侧的 flag 由 dsh-cmdline 提供：启动器把剩余参数以不可变快照 cmdlineArgs 服务注入，任何应用插件都可以注入它并解析自己的 flag。web 应用的 web-startup 插件（dsh-web-app/lib/startup.js）就是范例：用 commander 定义 --host/--port/--trusted-host，解析成功后 ctx.provide('webStartup', …)，再由配置行注入读取。

📌 安全设计 --host 0.0.0.0 被 web-startup 显式拒绝（源码里写明了「would expose remote code execution to the network」）。DSH 默认只绑 127.0.0.1。

3.2 启动器 flag 全集

flag含义
--profile <name>启动 $DSH_HOME/profiles/<name>；不存在的 profile 会从内置模板初始化（web/headless），其余需 dsh plugin 创建
--patch <path>追加一个补丁层覆盖（可重复），最后应用
--dump-config打印合并后的配置树并退出（含用户层与 --patch）
--dump-default-config只打印 bundle 层（不含用户层与 --patch），且不能与 --patch 同用
web 子命令--profile web 的别名，后跟 web 应用参数
plugin 子命令管理 profile 插件：dsh plugin --profile <name> <pnpm args>
-V/--version版本号

3.3 dsh plugin：在 profile 里装插件

每个 profile 目录自带 package.json 和 pnpm-workspace.yaml（共享 $DSH_HOME/profiles/node_modules）。dsh plugin 就是把参数原样转发给在该目录执行的 pnpm，因此 pnpm 的一切能力都可用：

# 从 npm 仓库装
dsh plugin --profile web add @some/dsh-plugin-xxx
# 装本地开发的插件(路径依赖)
dsh plugin --profile web add file:D:/code/my-dsh-plugin
# 看依赖关系 / 移除 / 更新
dsh plugin --profile web why @some/pkg
dsh plugin --profile web remove @some/pkg
dsh plugin --profile web update

安装后，你要么把它作为新行 insert: 进 cordis.patch.yml，要么它自己带 bundle patch 声明（见 CH.17）。

3.4 启动过程的时间线（预演 CH.9）

从 profile-boot 源码可以梳理出一次 dsh web 的完整启动：

  1. 解析启动器参数 → 得到 mode: profile 与 profile 名。
  2. composeProfile()：读 profile 的 package.json → 解析每个 bundle 的 cordis.patch.yml → 读用户层/家目录层/--patch → composeEntries() 用 applyEntryPatches 算出最终行表；重写 cordis.yml 为空根。
  3. boot()：new Context() → 设置 baseUrl → ctx.provide('dshHomePath', …) → 加载 Loader 插件 → 注入启动环境与 cmdlineArgs → mountRootInclude 把最终行表挂成 Entry 树 → 等 Loader 树稳定 → 校验所有行都激活成功。
  4. 启动后挂 HMR/定时器，并 watch 用户补丁文件 —— 这就是「改 patch 即热重载」的来源。
  5. 安装 SIGINT/SIGTERM 处理器：先优雅 dispose 整棵树（每个插件跑清理），超时 5 秒强制退出。

3.5 本章小结

  • 启动器 flag 在前，其余参数属于应用；帮助/版本/错误都以非零码退出。
  • dsh plugin 是 pnpm 的透传壳，用于管理 profile 的插件依赖。
  • 启动 = 叠补丁 + 建 Context + 挂 Loader + 等 Entry 树稳定 + watch 热重载。

第二部分 · Cordis 原理 —— 一切插件的内核

CH.4 Cordis 总览：为「可组合插件」而生的框架

4.1 设计动机

DSH 需要同时跑上百个插件：LLM 适配、会话持久化、十几个工具、沙箱、Web 服务器、浏览器端模块…… 它们之间有复杂的依赖关系（工具依赖工具注册表；Web 服务器依赖参数解析服务；子代理依赖 LLM 与会话）。传统做法是「写一个大对象到处 import」，而 Cordis 的答案是三个正交的抽象：

抽象回答的问题类比
Context（上下文）「我从哪来、依赖谁」—— 每个插件在哪个作用域里活依赖注入容器
Service（服务）「别人能用我什么」—— 具名 API，注册到 ctx 上接口 + 单例注册表
Plugin / Fiber（插件/纤维）「我怎么活、怎么死」—— 生命周期、资源清理、依赖就绪才启动可热插拔的模块

再加上事件总线（Events）做解耦通信，就构成了全部。

// 2. 注册一个服务(根 fiber 提供)
ctx.provide('greeter', { hello: (name) => `hello, ${name}` })

// 3. 加载一个插件:依赖 greeter 就绪后才会执行

注意几个细节，它们是 Cordis 的「签名」：

  • ctx.plugin() 返回一个 Fiber（可 await），而不是 Promise 本身。
  • 插件有 inject 声明后，不会立即执行，等服务可用才激活（这里是同步场景所以看不出，CH.7 详讲）。
  • ctx.on/emit/provide/plugin 都是「mixin」到 ctx 上的方法，真正实现在 ctx.events / ctx.reflect / ctx.registry 服务里。

CH.5 Context 与依赖注入的魔法：Proxy 与 ReflectService

5.1 ctx 是一个 Proxy

Context 构造函数最后一行是 return self，其中 self = new Proxy(this, ReflectService.handler)。也就是说：你拿到的 ctx 是一个代理对象，任何属性读/写都会先经过 ReflectService.handler 的 get/set 陷阱。这是 Cordis 全部「魔法」的物理基础。

5.2 get 陷阱：一次读取的完整旅程

简化后的 get 陷阱（reflect.ts 第 135 行起）逻辑：

  1. 特殊属性直通：symbol、prototype/then、纯数字字符串、_ 开头 —— 直接 Reflect.get，不参与服务解析（防止 Proxy 干扰内部机制）。
  2. 自有属性直通：ctx.events 这类直接定义在对象上的，直接返回（并套一层 trace 包装）。
  3. accessor 属性：如果 reflect.props[name] 声明为 accessor，调用其 get 钩子（mixin 就靠这个）。
  4. 服务解析：走 internal/get waterfall → 找到隔离标签 → 从当前 fiber 开始向上沿父 fiber 链找 fiber.store[name]：找到返回；若 name 在 inject 里但没就绪 → 报「cannot get required service in inactive context」；找不到实现 → 报「cannot get property X without inject」。
📌 为什么报错信息是「without inject」 因为 Cordis 的哲学是：不用 inject 声明就读取服务，要么是忘记声明（bug），要么是想读还没就绪的服务（也多半是 bug）。它把「依赖」变成显式声明，从而能自动编排加载顺序。如果你确实想「顺手读一下、没有就算了」，用 ctx.get(name)（不抛错、返回 undefined）。

5.3 set 陷阱与「只能自己改自己」

set 陷阱对称：对未声明属性的写入，非根 fiber 直接抛 cannot set property X without provide；对服务属性的写入走 internal/set waterfall，最终 reflect.set 会校验写者必须是提供该服务的 fiber（cannot set property in multiple fibers）。这防止了插件间互相乱改状态。

5.4 服务解析的核心：ReflectService 的 store

服务实现存在 reflect.store 里，键不是服务名，而是隔离标签（isolation label, 一个 symbol）：

// 概念模型
store: { [isolationLabelSymbol]: { name, value, fiber, check } }

// 提供服务:把实现挂到当前 fiber,并登记到 store
ctx.provide('llm', llmImpl)
// 读取服务(不要求 inject)
ctx.get('llm')
// 覆写(仅限提供者 fiber)
ctx.set('llm', newImpl)
  • provide(name, value, check?)：注册实现，返回一个 disposer；fiber 卸载时自动反注册，并唤醒（notify）所有依赖它的 fiber。
  • check：可选的就绪谓词。服务在但「还没准备好」时（如 Loader 的 await: true 拦截），依赖它的插件会保持 PENDING。
  • notify(names)：对每个依赖了这些服务的 fiber 重新 _checkImpl + _refresh —— 这就是依赖驱动的自动重载（CH.7）。

5.5 extend / isolate / intercept：三个「作用域手术」

Context 提供的三个方法都返回子上下文（原型链继承父，不修改父）：

方法效果典型用途
ctx.extend(meta)子 ctx 继承父的一切，meta 成为自有属性每个 fiber 的 ctx 都是 parent.extend({ fiber })；Loader 的 Entry 也 extend 一个 [Entry.key]
ctx.isolate(name, label?)子 ctx 里对服务 name 的读写换到新隔离标签；同 label 则合并作用域「每个 Agent 会话一个隔离的 service」——DSH 的会话隔离、agent scope
ctx.intercept(name, config)给 name 服务的「每插件配置」追加一段拦截配置Loader 的 inject 配置合并；ctx.inject(deps, cb) 的底层

isolate 是 DSH 实现多会话隔离的关键：每个 session 的 Agent 运行在 ctx.isolate('agent', sessionLabel) 之类的子上下文里，它的 session 服务与别的会话互不可见。

5.6 accessor 与 mixin：把服务方法「焊」到 ctx 上

  • ctx.accessor(name, { get, set? })：声明一个计算属性。注册进 reflect.props，fiber 卸载时移除。
  • ctx.mixin(source, keys)：为 source 服务的每个 key 生成一个转发 accessor（方法会 bind 到服务上）。核心服务就是这么混入 ctx 的：mixin('events', ['on','once','parallel','emit','serial','bail','waterfall'])。

这也是为什么你写 ctx.tools.register(...) 能工作：tools 服务把 register mixin 到了 ctx 上。

5.7 本章小结

  • ctx = Proxy；读取服务的路径：特殊属性 → 自有属性 → accessor → fiber 链上的 store。
  • 服务用 provide 注册、get 免声明读取、set 限提供者覆写、disposer 自动反注册并 notify 依赖方。
  • extend（继承）、isolate（隔离作用域）、intercept（拦截配置）是三个作用域手术。
  • mixin 把服务方法映射到 ctx 上，形成 DSH 里 ctx.xxx 的丰富表面。

CH.6 Service：DSH 的「服务」抽象

6.1 Service 是什么

Service 是 Cordis 里「注册在 ctx 上的具名能力」的基类（service.ts）。DSH 里几乎每个核心能力都是一个 Service 子类实例：session、llm、tools、shell、loader、jobs、systemPrompt、subagents、goals……

import { Service } from '@deepseek-ai/cordis'

// 定义一个服务:继承 Service,构造函数里 super(ctx, name) 即完成注册
class Greeter extends Service {
  // 静态 provide 字段:不传 name 时的默认服务名
  static provide = 'greeter'
  // 可选:Config 类型(拦截配置的 merge 也用它)
  static Config = { merge: (a, b) => ({ ...a, ...b }) }

  constructor(ctx, options = {}) {
    super(ctx, 'greeter')
    this.prefix = options.prefix ?? 'hello'
  }

  greet(name) {
    return `${this.prefix}, ${name}`
  }
}

// 作为插件加载:构造实例 → 注册服务 → fiber 卸载时自动反注册
ctx.plugin(Greeter, { prefix: '你好' })

console.log(ctx.greeter.greet('世界'))  // → 你好, 世界

6.2 Service 的「注册即生命周期」

Service 构造函数做了两件事：

  1. ctx.reflect.provide(name, self, check) —— 把实例注册为服务；provide 是 fiber effect，所以服务随提供它的 fiber 自动销毁。
  2. 若实例有 [Service.invoke] 方法，则返回一个「可调用对象」（函数 + 原型方法的合体），使 ctx.logger 可以 ctx.logger('name') 这样被调用。

因此「写一个服务」＝「写一个插件」：服务就是插件的产出。这也是 DSH 中「行」与「服务」几乎一一对应的原因。

6.3 Service 的关键静态 symbol（源码速查）

symbol含义
Service.init类插件实例构造后由 fiber 调用的初始化钩子（instance[init]?.()）
Service.check可用性谓词；provide 时传给 reflect，依赖方据此决定是否保持 PENDING（Loader 用它实现 await: true）
Service.invoke存在则服务变成可调用对象（如 ctx.logger()）
Service.extend派生扩展实例的助手（子作用域服务）
Service.resolveConfig把 intercept 链 + base + head 合并成最终配置（Loader 每插件的 inject 配置就走它）
Service.filter事件过滤：服务实例只收到同隔离标签的 ctx 派发的事件（ctx.on(..., {global:true}) 可绕过）

6.4 intercept 配置解析：Service.resolveConfig

当多个插件都「拦截」同一个服务的配置时（ctx.intercept('llm', {...}) 或 inject: { llm: {...} } 对象形式），[resolveConfig] 按 离根近的在前 的顺序把拦截段拼起来：

// 伪代码:intercept 是原型链,从根到当前逐层收集
configs = []                        // 祖先拦截段
while (name in intercept) { configs.unshift(intercept[name]); ... }
configs.unshift(base)               // 默认配置垫底
configs.push(head)                  // 最优先配置收尾
return Config.merge ? Config.merge(...configs) : Object.assign({}, ...configs)

这解释了 DSH 里「每个会话可以给同一个服务不同的参数」：会话作用域上 intercept('agent', …)，子 ctx 里的插件读到的就是被拦截后的配置。

6.5 本章小结

  • Service 基类 = 注册即生命周期：构造即 provide，卸载即销毁。
  • 服务的可调用性（invoke）、可用性（check）、拦截配置（resolveConfig）、事件过滤（filter）都由静态 symbol 表达。
  • 「服务即插件产物」—— 理解这一点，DSH 的插件世界就清晰了。

CH.7 Plugin 与 Fiber：插件的生命与依赖编排

7.1 插件的三种形态

registry.ts 定义了 Plugin 联合类型，注册表用 resolve() 归一化成「可执行回调」：

// ① 函数式:(ctx, config) => any
const plugin = (ctx, config) => { ctx.on('x', ...) }
plugin.name = 'my-plugin'
plugin.inject = ['tools']
plugin.Config = z.object({ ... })

// ② 类式:new (ctx, config) => any
class MyPlugin {
  static inject = ['tools']
  static Config = z.object({ ... })
  constructor(ctx, config) { ... }
}

// ③ 对象式:{ apply(ctx, config) }
const plugin = {
  name: 'my-plugin',
  inject: ['tools'],
  Config: z.object({ ... }),
  apply(ctx, config) { ... },
}

三种形态的公共元数据（Plugin.Base）：name（显示名）、Config（标准 schema 校验器）、inject（依赖声明：数组或对象，对象值=该服务的拦截配置）、provide（本插件提供的服务名）、intercept。

7.2 RegistryService：插件注册表

registry.ts 内部维护 _internal: Map<callback, Runtime>：

  • Runtime 以「可执行回调」为键 —— 同一个插件被 ctx.plugin() 多次调用，共享一个 runtime，产生多个 fiber。
  • ctx.plugin(plugin, config)：校验形态 → 建/取 runtime → new Fiber(ctx, config, resolvedInject, runtime) → 返回「可 await 的 fiber」。
  • ctx.inject(deps, callback) 是 plugin({ inject, apply }) 的语法糖。
// registry.ts 核心(节选)
plugin(plugin, config, getOuterStack) {
  const callback = this.resolve(plugin)          // 函数 / 类的构造器 / apply
  if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method')
  let runtime = this._internal.get(callback)     // 复用或新建
  if (!runtime) {
    runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
    this._internal.set(callback, runtime)
  }
  const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
  // 返回 PromiseLike: await fiber 会等它 settle
  return wrapped
}

7.3 Fiber：一次插件加载 = 一个纤维

Fiber（fiber.ts）是 Cordis 最重要的类。每个插件激活实例对应一个 fiber，它持有：

  • uid：注册表计数器分配的全局唯一 id（0 是根 fiber）；dispose 后置 null。
  • ctx：parent.extend({ fiber: this }) —— 插件运行在专属子上下文。
  • inject：解析后的依赖表（服务名 → 拦截配置）。
  • _store：当前已解析的依赖实现快照。
  • _disposables：effect 产生的清理器列表（后进先出执行）。
  • state：生命周期状态机。

7.5 effect 系统：插件的资源纪律

ctx.effect(execute, label?) 是 Cordis 的资源管理核心。它立即执行 execute，收集其返回的 disposer，在 fiber 卸载时逆序执行所有 disposer：

ctx.effect(() => {
  const timer = setInterval(() => tick(), 1000)
  // 返回清理函数:卸载时自动执行
  return () => clearInterval(timer)
}, 'my interval')

ctx.effect(function* () {
  const a = ctx.on('x', fn1)      // on 返回 disposer
  yield a
  const b = ctx.provide('svc', v) // provide 返回 disposer
  yield b
}, 'my resources')
  • 接受函数 / Promise / (async) 可迭代对象；非法返回值抛 Invalid effect。
  • 效果带 label 与嵌套树（EffectMeta），fiber.getEffects() 可诊断。
  • 已 dispose 的 fiber 再注册效果会抛 CordisError('INACTIVE_EFFECT')。
  • ctx.on / ctx.provide / ctx.plugin 全部基于 effect —— 所以插件卸载时，事件监听、服务、子插件全部自动清理，这是 DSH 能安全热重载的根基。

7.6 本章小结

  • 插件三种形态（函数/类/对象），注册表以回调为键建 runtime，一次加载一个 fiber。
  • Fiber 状态机：PENDING→LOADING→ACTIVE⇄UNLOADING，FAILED/DISPOSED 为终态；依赖驱动重载。
  • effect 系统 = 声明式资源清理，逆序执行；它是热重载安全的根基。

CH.8 事件总线：五种派发模式与 internal 钩子

8.1 事件总线的角色

服务解决「依赖」，事件解决「解耦」：插件间不知道彼此存在，只通过事件名通信。Cordis 的事件总线（events.ts）比普通 EventEmitter 强在三点：

  • 五种派发模式，覆盖同步/异步/短路/洋葱等需求。
  • 上下文过滤：监听器默认只收到「同一隔离作用域」派发的事件（{global: true} 绕过）。
  • 生命周期自动清理：ctx.on 是 effect，fiber 卸载自动移除。

8.2 五种派发模式（速查表）

方法行为返回值适用场景
ctx.emit(name, ...args)同步调用所有监听器，不等待 Promisevoid通知类（日志、UI 刷新）
await ctx.parallel(name, ...)并发执行并等待全部Promise<void>（有错抛 AggregateError）需要全部完成的通知
await ctx.serial(name, ...)按顺序 await，遇到「bail 值」提前停首个 bail 值「谁先处理谁赢」
ctx.bail(name, ...)同步版 serial（不 await）首个 bail 值同步短路（如 internal/listener 拦截）
ctx.waterfall(name, ..., next)洋葱模型：每个监听器包一层，调 next() 才继续最外层返回值中间件/可否决的管道（config 解析、update 提交流水线）
📌 bail 值定义 isBailed(v) = v !== null && v !== false && v !== undefined —— 返回 null/false/undefined 表示「不拦截，继续」。

8.3 waterfall 的洋葱模型

// 注册两个监听器,后者先注册先执行(默认 push 尾部,prepend 可插队)
ctx.on('fetch', (url, next) => {
  console.log('before', url)
  const result = next()          // 调用链上的下一个
  console.log('after', result)
  return '[' + result + ']'      // 返回值会继续向上传递
})
ctx.on('fetch', (url, next) => {
  return 'content-of-' + url     // 最内层:不调 next 就到此为止
})

ctx.waterfall('fetch', '/a', () => 'base')
// → before /a
// → after content-of-/a
// 返回 '[content-of-/a]'

DSH 里 waterfall 随处可见：internal/config（插件配置解析管线）、internal/update（配置更新流水线，Loader 在里面做持久化写回）、internal/get/internal/set（服务读写的拦截链）。

8.4 上下文过滤（filter）

每个 ctx 可以带 [Context.filter] 谓词（ctx.on 时由 dispatch 检查）：派发时 thisArg?.[Context.filter]?.(hook.ctx) 为假则跳过该监听器。Service 的默认 filter 是「监听器 ctx 与派发 ctx 的服务隔离标签一致」—— 这就是 DSH 多会话下事件互不串台的基础。

8.5 internal/* 事件：框架的「可插拔内脏」

Cordis 把自身的核心操作也做成事件，让 Loader、HMR、持久化能无缝介入。这是理解 DSH 一切「魔法」的关键表：

事件模式载荷谁在用
internal/pluginemitfiberLoader 记录 entry↔fiber 映射、检测自我 dispose
internal/statusemitfiber, oldState状态监控
internal/configwaterfallconfig, nextLoader 对配置做 !!js 插值（interpolate）
internal/updatewaterfallconfig, noSave, nextLoader 持久化写回、reload 日志；HMR 否决
internal/get / internal/setwaterfallctx, name, value/error, next服务读写的统一拦截点（proxy 每次读取都过这里）

8.6 本章小结

  • 五种派发模式：emit / parallel / serial / bail / waterfall。
  • 监听器默认受上下文过滤；on/once 都是 effect，随 fiber 清理。
  • 框架内脏是 internal/* 事件 —— Loader、持久化、HMR 都是「监听这些事件的插件」。

CH.9 Loader 与补丁引擎：配置如何变成运行的插件

9.1 Loader：Entry 树

前八章我们认识了 Cordis 内核；现在看 DSH 如何把「patch 出来的行」变成真正运行的插件。cordis-plugin-loader 提供 Loader 服务（ctx.loader），它把配置组织成一棵Entry 树：

  • EntryTree：一棵树的根，负责按 baseUrl import 插件模块、write() 持久化。

9.2 Loader 如何「接管」Cordis 内核

Loader 本身是一个插件，它的构造函数里注册了几个全局监听器（源码 cordis-plugin-loader/src/index.ts），这是它「魔法」的全部：

监听Loader 做的事
internal/plugin把新 fiber 关联到它的 entry（fiber.entry = …），并把 entry 的 inject 合并进 fiber 的依赖表；检测「插件自我 dispose」→ 把该行标记 disabled: true 并写回磁盘
internal/config对 entry 行的配置做 interpolate() —— 递归求值 !!js 表达式（group/include 等载体行除外）
internal/update插件 update() 后把新配置写回 entry 并持久化（unparse 化简）；打印 reload 日志

换句话说：Loader 不用改 Cordis 一行代码，只靠 internal 事件就实现了「配置↔插件」的双向绑定。这就是 CH.8 那张 internal 表的价值。

9.3 Entry.update：三种更新路径

entry.update(options) 比较新旧配置算出 diff，然后分三路：

  1. 只改 config：fiber.update(newConfig, true) 原地热更（走 internal/update 流水线，持久化照常）。
  2. 改 name/inject/group：先 dispose 旧 fiber，import 新模块再启动 —— 换插件。
  3. 变 disabled：dispose 旧 fiber，行停用。

任一失败都会回滚到旧状态（源码里大量 rollback 分支），保证热重载的原子性。

9.4 补丁引擎：applyEntryPatches 精读

补丁语义实现在 dsh-app-boot/lib/index.js 的 applyEntryPatches(data, patches, warn)（CH.2 讲过三条规则，这里是精确行为）：

// 1. 深拷贝输入(绝不原地改,热重载才能回退)
data = structuredClone(data)
// 2. 建立 id → entry 索引(递归进 group)
entryMap = new Map(); buildMap(data)
// 3. 逐个应用 patch
for (const patch of patches) {
  const { id, insert, name, ...overrides } = patch
  if (insert) {                    // 插入:顶层或 id 指定的 group 内
    if (id) { target = entryMap.get(id); target.config.push(...insert) }
    else data.push(...insert)
    buildMap(insert)               // ★ 刚插入的行立即可被后续 patch 寻址
    continue
  }
  if (!id) { warn('id is required'); continue }
  target = entryMap.get(id)
  if (!target) { warn('entry not found'); continue }
  if (name && name !== target.name) { warn('name mismatch'); continue }  // 防呆
  for (const [k, v] of Object.entries(overrides)) target[k] = v           // 整键覆盖
}

注意 config 覆盖是「整体替换 target.config」，disabled 也是直接赋值 —— 所以「禁用一行」只要 - id: x \n disabled: true。

9.5 热重载是怎么发生的

watchUserPatches（app-boot）监听 profile 层与家目录层补丁文件的变更：文件变化 → 重新读全部补丁层 → 重算行表 → root.update(新行表) → Entry 树 diff 出增删改 → 逐个 Entry.update。所以你改 cordis.patch.yml 保存，几秒内新配置就生效，日志里能看到 reload plugin %C。

⚠️ 热重载的边界 只有「行级」变化能热更。改 dsh.profile.bundles（换组合包）、改依赖版本、改 JS 代码本身，需要重启进程。前端插件（浏览器侧）的代码热更走 dsh-client-hmr + pnpm run dev:web 构建 watcher。

9.6 本章小结

  • Loader 用 Entry 树管理「配置行 ↔ 插件 fiber」；靠 internal/* 事件与内核解耦。
  • Entry.update 分三条路径（热更 config / 换插件 / 停用），失败回滚。
  • 补丁引擎：深拷贝 → id 索引 → insert/覆盖/禁用，后写胜出。
  • 文件 watcher 驱动热重载，配置即代码的真正含义在此。

CH.11 服务生态巡礼：LLM、会话、Agent、子代理、目标、工作流

11.1 按「领域」给服务分组

DSH 的服务可以分成几个清晰的领域。理解每个领域 = 知道「模型调用一次工具时，后台发生了什么」。

11.2 模型层：llm / llm-deepseek / llm-pi-ai / llm-retry

  • ctx.llm：模型调用门面，按 provider/model 路由到适配器。

11.3 会话层：session 家族

会话（session）是 DSH 的「一次对话/一个任务」单元：

  • agent：Agent 注册表与核心类型 —— 一个 Agent = 一个会话的「模型执行者」，携带自己的工具集、提示词段、委托后端。

  async execute(args, exec) {    // ★ 真正干活的地方
    // args  = 模型传参(已按 schema 校验)
    // exec  = { agent, callId, signal, … }  执行上下文
    return 'hi ' + args.who
  },
  // 以下全部可选:
  // finalizeContent(exec, result)   — 内容最终化钩子
  // presentCall(args)               — 调用卡的展示
  // presentResult(args, result)     — 结果卡的展示
  // isConcurrencySafe(args)         — 是否可并发
  // timeoutMs                       — 工具级超时
}))

12.3 参数与输出 schema 的「隐式编译」

defineTool 内部把你写的「属性声明」编译成严格 JSON Schema：parameters 变成 object 根 schema，output.schema 原样校验。模型每次调用都会先过校验（validateJsonSchemaValue），非法参数抛 ToolArgsError（invalid arguments: …），而不是让 execute 收到脏数据。支持的类型：string / number / integer / boolean / null / array / object / oneOf，属性支持 required / enum / const / description。

📌 为什么输出也要 schema execute 的返回值同样按 output.schema 校验。这一方面保证 UI 渲染器拿到的数据形状稳定（replay 旧日志时也能软校验回退到通用渲染），另一方面让工具作者把「契约」写清楚。

12.4 渲染与展示：presentCall / presentResult / render

DSH 的 Web UI 不是「模型说什么就显示什么」，而是由工具定义驱动：

  • presentCall(args)：模型发起调用时，UI 画一张「调用卡」。pwsh 返回 {card:'terminal', title: command, description}；后台任务返回 generic 卡。
  • presentResult(args, result)：结果卡。pwsh 把退出码解析成「exit code pill」，输出区单独渲染。
  • output.render(args, value)：把结果值变成模型/日志可见的文本块序列 —— 这是「模型看到什么」的最后一公里。

12.5 工具注册表：register / restrict / 分层作用域

  • ctx.tools.register(definition)：全局或调用方 agent 作用域注册；重名（同层）抛错；run_code 是保留名（Code Mode 的传输工具）。
  • ctx.tools.restrict({ allow?, deny? })：为调用方 agent 作用域屏蔽全局工具（白/黑名单）；只能在有 agent 作用域的 ctx 上调用。
  • 作用域分层：全局层 + 各 agent 层，scoped 工具遮蔽全局同名工具；每个会话/agent 看到的工具集 = 全局 − 限制 + 自身。
  • tools 行有 mode 配置：native | code | both（DSH_TOOLS_MODE 环境变量临时开关）。code 模式只暴露 run_code，由代码运行时解释执行。

12.6 工具插件的最小完整形态（本教程第一个工具）

// 文件名: lib/index.js —— 这就是一个完整可用的 DSH 工具插件

import { defineTool } from '@deepseek-ai/dsh-tools'

// ★ 这三个具名导出是 Cordis 加载器的约定
export const name = 'tool-hello'               // 插件名(日志/诊断用)
export const inject = ['tools', 'systemPrompt'] // 依赖:工具注册表 + 提示词段服务
export const Config = z.object({                // 插件配置 schema(行 config 会被校验)
  greeting: z.string().default('你好'),

  // 1. 往系统提示词里塞一段,让模型知道有这个工具
  ctx.systemPrompt.section({
    name: 'tool:hello',
    order: 200,

  // 2. 注册工具
  ctx.tools.register(defineTool({
    name: 'hello',
    description: '返回一句问候语,问候对象是 who 参数指定的名字。',
    parameters: {
      who: { type: 'string', required: true, description: '问候对象的名字' },

      schema: { type: 'string' },

  }))
}

CH.13 沙箱、权限与审批：安全模型

13.1 三层安全模型

DSH 的权限模型可以概括为「模式（mode）→ 沙箱（sandbox）→ 审批（approval）」三件套。base 补丁里对应的行：

行职责
sandbox-policy读 DSH_PERMISSION_MODE（默认 workspace-write）与 process.cwd()，决定当前进程的沙箱模式
sandbox（dsh-sandbox-local）文件沙箱实现：read-only / workspace-write / danger-full-access
bash-sandbox / pwsh-sandbox平台对应的命令沙箱（Windows 用 pwsh-sandbox；bash-sandbox 在 win32 上 disabled）
approval（dsh-user-approval）审批通道：danger-full-access 模式自动 never 审批；否则 ask
permission（dsh-permission-presets）预设三档：read-only / workspace-write / danger-full-access（各自映射 sandbox+approval）

13.2 三种模式的定义

# base 补丁里的 permission 行 —— 模式就是「预设的组合」
- id: permission
  name: '@deepseek-ai/dsh-permission-presets'
  config:
    presets:
      read-only:
        sandbox: read-only          # 只能读
        approval: ask
      workspace-write:              # ★ 默认
        sandbox: workspace-write    # 只能写工作区
        approval: ask               # 越界操作要问用户
      danger-full-access:
        sandbox: danger-full-access # 全放开
        approval: never             # 不再问

13.3 工具调用时的权限流转（以 pwsh 为例）

回到 dsh-tool-pwsh/lib/index.js（CH.15 会仿写），它的 execute 里权限逻辑是：

  1. ctx.shell.sandboxMode 拿到当前会话的沙箱模式（无沙箱执行器则整个 escalation 参数都不展示）。
  2. 调用前解析「standing policy」：ctx.get('sandboxPolicy').resolve({ session })。
  3. 若模型请求了 sandbox_permissions（升权）：走 approveEscalation() —— 校验严格拓宽方向（不能从 read-only 直接跳 full）、经 ctx.approval 向用户弹审批、映射结果。
  4. 最终把 { mode, workspaceRoot, … } 作为 sandboxPolicy 传给执行器；执行器在受限进程里跑命令，把 denied 标记带回来。
  5. 渲染时：被拒 → [sandbox: file access denied under <mode> mode] 标记 + 升权提示（escalationHintMarker）。
⚠️ 安全设计要点（源码里的明文规则）
  • 升权是「一次性重试」：先被拒，再带 sandbox_permissions + justification 重试同一条命令；禁止绕道聊天问权限、禁止预先投机升权。
  • Windows 沙箱下 read-only 模式跑 PowerShell ConstrainedLanguage；进程间捕获输出（named pipe）被禁 → 模型会看到 EPERM 边界提示。
  • 升级请求的批准弹窗就是用户的「同意」—— 不需要额外确认。

13.4 你可以在配置里改什么

# 例子:让 web profile 直接全放开(仅限可信环境!)

  config:
    mode: danger-full-access
    workspaceRoot: !!js process.cwd()
# 或:只读模式
- id: sandbox-policy
  config:
    mode: read-only
⚠️ 这不是安全边界 DSH 的沙箱是「事故防线」而不是「安全墙」—— 它是给模型自己设的护栏，防止它乱写文件/乱跑命令。别把它当多租户隔离用。

13.5 本章小结

  • 模式 = 预设组合（sandbox + approval）；默认 workspace-write + ask。
  • 工具执行前解析 standing policy；升权是一次性、带理由、经审批的重试。
  • 被拒、超时、信号、退出码都渲染成模型可见的标记 —— 模型据此决策。

14.2 插件本体：提供「一个服务 + 一个事件监听」

// lib/index.js —— 一个服务插件:提供 ctx.helloWorld 服务,并响应事件
import z from '@deepseek-ai/schemastery'

export const name = 'hello-world'
// 不 inject 任何东西;服务插件通常要 provide 什么,但这里用 ctx.provide 即可
export const Config = z.object({
  prefix: z.string().default('DSH'),
})

export function apply(ctx, config) {
  // 1) 提供服务 ctx.helloWorld(根 fiber 提供,随插件卸载自动移除)
  ctx.provide('helloWorld', {
    greet(name) {
      return `[${config.prefix}] hello, ${name}!`
    },
  })

  // 2) 监听框架事件:每次插件状态变化打印日志
  ctx.on('internal/status', (fiber, oldState) => {
    ctx.logger('hello').info('fiber %s: %s -> %s',
      fiber.name, oldState, fiber.state)
  })

  // 3) 注册一个自己的事件并派发(演示事件总线)
  ctx.on('hello/greet', (name) => {
    ctx.logger('hello').info('greet %s', name)
  })

  // 4) 返回 disposer:插件卸载时执行(可选)
  return () => {
    ctx.logger('hello').info('hello-world unloaded')
  }
}

15.3 插件本体

// lib/index.js
import z from '@deepseek-ai/schemastery'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'tool-weather'
// 依赖:工具注册表、提示词段、可选的天气数据源服务
export const inject = ['tools', 'systemPrompt']
export const Config = z.object({
  defaultUnit: z.string().default('celsius'),
  maxCitiesPerCall: z.number().min(1).max(10).default(3),
})

export function apply(ctx, config) {
  // 提示词段:告诉模型这个工具的存在与边界
  ctx.systemPrompt.section({
    name: 'tool:weather',
    order: 210,
    text: 'weather 工具返回静态示例天气数据;数据源可通过 ctx.weatherSource 服务替换。',
  })

  // 若已有别的插件提供 weatherSource,用它的;否则用内置的静态源
  const source = ctx.get('weatherSource') ?? {
    async fetch(city) {
      const table = {
        北京: '晴, 24°C', 上海: '多云, 27°C', 深圳: '阵雨, 29°C',
      }
      return table[city] ?? `暂无 ${city} 的数据`
    },
  }

  ctx.tools.register(defineTool({
    name: 'weather',
    description: '查询一个城市的天气。支持中文城市名;一次最多查询 ' +
      config.maxCitiesPerCall + ' 个城市。',
    parameters: {
      cities: {
        type: 'array',
        required: true,
        description: '要查询的城市列表',
        items: { type: 'string' },
      },
    },
    output: {
      schema: {
        type: 'object',
        additionalProperties: false,
        properties: {
          reports: {
            type: 'array',
            required: true,
            items: {
              type: 'object',
              additionalProperties: false,
              properties: {
                city: { type: 'string', required: true },
                text: { type: 'string', required: true },
              },
            },
          },
        },
      },
      // 模型最终看到的文本
      render: (_args, value) => [{
        type: 'text',
        text: value.reports.map(r => `${r.city}: ${r.text}`).join('\n'),
      }],
    },
    async execute(args) {
      if (args.cities.length > config.maxCitiesPerCall) {
        throw new Error(`一次最多查询 ${config.maxCitiesPerCall} 个城市`)
      }
      const reports = []
      for (const city of args.cities) {
        reports.push({ city, text: await source.fetch(city) })
      }
      return { reports }
    },
    // UI:调用卡
    presentCall: (args) => ({
      card: 'generic',
      title: `weather: ${args.cities.join(', ')}`,
      kind: 'execute',
      content: [{ type: 'text', text: '查询天气' }],
    }),
    // UI:结果卡
    presentResult: (args, result) => ({
      card: 'generic',
      content: [{
        type: 'text',
        text: result.content[0]?.text ?? '',
      }],
    }),
  }))
}

把数据源做成独立服务插件，weather 工具只负责消费 —— 这是 DSH 的惯用分层：

export function apply(ctx) {

    async fetch(city) {
      // 这里可以真的调 API / 读文件 / 查数据库
      const res = await fetch(`https://api.example.com/weather?city=${encodeURIComponent(city)}`)
      return (await res.json()).text
    },
  })
}

- insert:
    - id: weather-source
      name: '@me/dsh-weather-source'
    - id: tool-weather
      name: '@me/dsh-tool-weather'

CH.16 配置 Schema 与 Schemastery 深入

16.1 为什么需要 Config schema

插件的 Config 是一个 Standard Schema 校验器。加载插件时，resolveConfig() 用 Config['~standard'].validate(config) 校验行配置，失败抛 ValidationError（逐条列出 issues 与路径），fiber 进入 FAILED。好处：

  • 配置错误在启动时暴露，而不是运行到一半才崩。
  • schema 同时是 Web Settings 页的自动表单（元数据：default、description、role… 驱动 UI）。
  • schema 可以带 merge，决定 intercept 配置怎么合并（CH.6.4）。

16.2 Schemastery 快速参考

DSH 使用 @deepseek-ai/schemastery（schemastery 3.x 的 fork，兼容 standard-schema）。常用构造器：

import z from '@deepseek-ai/schemastery'

export const Config = z.object({
  // 基础类型 + 默认值
  name: z.string().default('unnamed'),
  count: z.number().min(0).max(100).default(10),
  enabled: z.boolean().default(true),
  tags: z.array(z.string()).default([]),
  // 必填
  apiKey: z.string().required(),
  // 枚举/常量
  mode: z.union([z.const('fast'), z.const('safe')]).default('safe'),
  // 字典/嵌套
  providers: z.dict(z.object({ url: z.string() })).default({}),
  // 转换(输入→输出)
  timeout: z.transform(z.string(), (s) => Number(s)).default('5000'),
  // 延迟递归
  tree: z.lazy(() => z.object({ value: z.string(), child: z.union([z.any()]).optional() })),
})

z.string()/z.number()/z.boolean()基础类型；链式 .min/.max/.default/.required/.description()
z.object({…})对象；键→schema
z.array(inner) / z.tuple([…])数组/元组
z.dict(inner, keySchema?)任意键映射
z.union([…]) / z.intersect([…])联合/交叉
z.const(v)字面量
z.transform(inner, fn)校验后转换（配置归一化）
z.lazy(fn)递归 schema

16.3 Config 的 merge 与 intercept（进阶）

}

CH.18 定制自己的 Profile 与 Bundle 组合

18.1 为什么需要自定义 Profile

内置的 web/headless 是「开箱即用」的形态。当你想要「一个没有 Web、没有浏览器插件、只有命令行任务 + 自定义工具的极简形态」，或「一套内部团队专用的组合」，就应该建自己的 profile。

18.2 创建一个自定义 Profile

# 1) 创建目录与 package.json(web/headless 之外的 profile 必须手动初始化)
mkdir $env:USERPROFILE\.dsh\profiles\cli
# profiles\cli\package.json:

{
  "name": "dsh-profile-cli",
  "private": true,
  "dependencies": {},
  "dsh": {
    "profile": {
      "bundles": ["@deepseek-ai/dsh-base"]
    }
  }
}

# 2) 用 dsh plugin 补全依赖(会创建 pnpm-workspace.yaml 并安装)
dsh plugin --profile cli add @deepseek-ai/dsh-base

# 3) 首次启动会生成 cordis.yml / cordis.patch.yml
dsh --profile cli --dump-config    # 先看最终配置
⚠️ 没有 runner 的 profile 不会「做任何事」 只有 base 的 profile 只是一个「加载了所有基础插件但没有表面」的空壳 —— 它没有 headless-runner 也没有 web-startup，所以 dsh --profile cli 会启动后挂着。你的 profile 至少要有一个「应用插件」：要么模仿 headless 加 runner，要么模仿 web 加 web 层。照抄 dsh-headless/cordis.patch.yml 是最快的起步。

18.3 组合策略：层叠而不是分叉

DSH 的设计鼓励「共享 base + 各自 surface」，而不是复制粘贴配置：

  • 所有 profile 共享 dsh-base —— 升级即全部受益。
  • 你的定制放 cordis.patch.yml（profile 级）或 $DSH_HOME/cordis.patch.yml（机器级，所有 profile 生效）。
  • 临时实验用 --patch overlay.yml，不动任何文件。
  • 「一整块能力」打成 Bundle（CH.17.2），加一行 bundles 即可复用。

- id: web-runtime
  config:
    printUrl: false
- id: session-query-sqlite
  config:
    path: 'D:/data/dsh/search.db'
    openAt: first-search

dsh --profile web --patch deploy-extra.yml

18.5 本章小结

  • 自定义 profile = 目录 + package.json 声明 bundles；表面层要自己配。
  • 共享 base + surface 覆盖 + 用户层 + --patch 是最佳实践。
  • --patch 让部署差异不污染配置文件。

CH.19 Patch 语言精通：组合、插值、热重载实战

19.1 patch 文件的结构与语义回顾

# patch 文件 = 一个 YAML 数组,元素只有两种:
# ① 目标覆盖(必须有 id)
- id: some-row
  config: { … }        # 整体替换该行 config
  disabled: true       # 禁用
  name: 'other-pkg'    # 换插件(会触发 换插件 更新路径)
  inject: [svc]        # 改依赖

# ② 插入列表(可带 id 指定插入到哪个 group)
- insert:
    - id: new-row
      name: 'pkg'
      config: { … }
    - id: nested
      group: true
      config:
        - id: child-row
          name: 'pkg2'

19.2 组合模式：按需组装一个「超级工具集」

一个常见的需求：给 Web 的默认 agent 换一组工具。做法是写自己的 agent preset（CH.20 详讲），或直接覆盖 tools 行与相关行。这里演示更常用的「覆盖 + 插入」组合拳：

# $DSH_HOME/profiles/web/cordis.patch.yml
# 1) 调整现有行的行为
- id: tool-result-pruner
  config:
    thresholdChars: 16384      # 让模型看更长的工具输出
- id: repeat-tool-reminder
  config:
    thresholds: [4, 8]         # 改提醒节奏

# 2) 插入自己的工具
- insert:
    - id: tool-weather
      name: '@me/dsh-tool-weather'
      inject: [weatherSource]
    - id: weather-source
      name: '@me/dsh-weather-source'

# 3) 关闭不需要的
- id: skill-badge
  disabled: true

保存即热重载 —— 这是 DSH 最爽的体验之一。

19.3 !!js 插值的精确定位

  • 求值时机：插件 fiber 激活前，internal/config 里由 Loader 对行配置递归插值（interpolate：递归替换 {__jsExpr} 节点）。
  • 作用域：with (ctx) { eval(expr) } —— 表达式里可以直接写 ctx.xxx、process、以及 ctx 上的一切（dshHomePath 由 boot provide）。
  • 时机陷阱：ctx.webStartup 只有在 web-startup 插件 provide 之后才存在 —— 所以依赖它的行必须写 inject: [webStartup]，否则表达式求值时服务还不存在（这正是 web-app 补丁里每行都带 inject 的原因）。
# 可用的表达式示例
port: !!js ctx.webStartup.port ?? 3080          # 服务值 + 默认值
mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'  # 环境变量
disabled: !!js process.platform === 'win32'     # 平台判断
root: !!js dshHomePath('sessions')              # home 路径助手
⚠️ 插值≠模板 !!js 是执行 JS 表达式，不是字符串模板。别写 "{{model}}" 这类 —— 那是 system-prompt 的 persona 模板变量（由 system-prompt 插件自己渲染），不是 loader 的插值。

19.4 热重载实战：改配置不停机

  1. 改 cordis.patch.yml 保存。
  2. watcher 触发 → 重算行表 → Entry.update 逐行 diff。
  3. 只改 config 的行：fiber.update 原地热更（插件代码不重跑，apply 不重新执行 —— 只有 fiber.update 内部逻辑会跑）。
  4. 改 name/inject/group 的行：卸载旧 fiber + 导入新插件 + 启动新 fiber（apply 重跑）。
  5. 新增/删除行：对应 insert/移除。
📌 常见误区 很多人以为「热重载 = 改 config 后 apply 重跑」。实际上纯 config 变化只触发 fiber.update（fiber.ts 的 update() 里 config 已被 _resolveConfig 处理过），插件代码体不会重新执行。想让代码响应配置变化，要么监听 internal/update，要么换插件路径（改 name）。

19.5 本章小结

  • patch 只有两种元素：目标覆盖与插入；group 支持嵌套。
  • !!js 在 fiber 激活前求值，作用域是 ctx + process；依赖服务必须先 inject。
  • 热重载分「原地热更 config」与「换插件重启」两种路径。

CH.20 会话、Agent 与 Agent Presets 的深层机制

20.1 一次模型调用全链路（把 CH.10–13 串起来）

你在 Web 输入框发一条消息，后台发生什么：

  1. 会话创建：客户端通过 api-gateway（host 平面的传输无关分发面）请求创建 session；session 携带 header（cwd、agent 引用）。
  2. Agent 挂载：Web 表面为会话挂一个 agent preset（默认 standard）—— preset 是一个组合：在会话作用域里激活一组行（工具插件、提示词段、委托后端）。这就是 base 里那些 tool-* 行在 Web 被禁用、改由 preset 挂载的原因。
  3. 工具集组装：preset 里每个工具插件 ctx.tools.register(...)；tools 服务按作用域算出模型可见工具集（全局 − restrict + 会话层）。
  4. 提示词组装：systemPrompt 把所有 section 按 order 排好（persona=0、harness:source=-99、plan-mode、tool:* 段…）。
  5. 请求发出：agent-loop/会话驱动器调 ctx.llm → llm-deepseek 适配器 → 解析凭证 → 请求模型（流式）。
  6. 工具执行：模型返回 tool_calls → 按工具名查注册表 → defineTool 校验参数 → execute（内部再走 shell/sandbox/jobs 等）→ render 回填。
  7. 持久化：每条消息写入 session JSONL；checkpoint 策略在请求前落检查点；投影更新（todos/goals/stats）。

这条链上每一步都是一个「行/服务/注册表」，你可以逐个替换 —— 这就是 DSH 的可定制性。

20.2 Agent Preset 详解

  • preset 是什么：一份「组合清单」—— 一个 preset 激活后，会话里就有哪些行。它是 Web 多会话架构下「每会话一套工具」的实现方式。
  • 来源：随部署的 config/agent-presets/（system trust，只读）+ $DSH_HOME/.agent-presets（用户/agent 自建，与 shell 同权）。
  • 默认：agent-presets 行配置 default: standard。
  • 预设内容：每个 preset 组合「哪些工具、哪些提示词段、哪个模型、什么委托后端」—— 从 base 补丁看，标准 preset 大概对应 base 里被 Web 禁用的那一组 tool-* 行（bash/pwsh/fs/goal/subagent/workflow/todo/web…）。
# 给自己建一个「纯文件阅读」preset(示例结构,字段以实际为准)
# $DSH_HOME/.agent-presets/reader.yml  (或 .json)
name: reader
rows:
  - id: tool-fs
    name: '@deepseek-ai/dsh-tool-fs'
  - id: tool-fs-search
    name: '@deepseek-ai/dsh-tool-fs-search'
  - id: tool-str-replace-editor
    name: '@deepseek-ai/dsh-tool-str-replace-editor'
# 然后在设置里把默认 preset 切到 reader,或让会话显式指定
⚠️ 上面的示例是「结构示意」 agent-presets 包有自己精确的 schema，字段名请以 @deepseek-ai/dsh-agent-presets 的 README 与配置 schema 为准；Web 的 Settings → Agent preset 页面会列出当前部署支持的所有预设。先读 README 再动手。

20.3 会话隔离与作用域（联系 CH.5 的 isolate）

  • 每个会话的 agent 跑在隔离作用域里：它的 session、agent 服务、投影、目标都互不可见。
  • host 平面的服务（loader、jobs 注册表、subagents 注册表、goals 服务、token-meter、api-gateway）对所有会话共享 —— 这正是 web-app 补丁注释里反复论证的「host-plane ownership」。
  • 子代理（subagent）是会话里的新「执行者」：spawn 全新、fork 继承；它们能 send_message 回父会话。

20.4 目标（Goal）与计划模式（Plan Mode）

  • Goal：持久化「同会话长期目标」，跨自动续跑轮次存活；goal-round-driver 驱动轮次；UI 的 GoalBar 显示在输入区。
  • Plan Mode：模型被一整段提示词约束（CH.11.6）—— 先调研、出决策完备的计划、用 exit_plan_mode 提交审批；审批后才是实施。你可以完全自定义这段提示词（覆盖 plan-mode 行的 section）。

20.5 本章小结

  • 模型调用全链路 = 会话 → agent(preset) → 工具集/提示词 → llm → 工具执行 → 持久化。
  • Agent preset 是 Web 多会话的「每会话组合」机制；host/agent 平面分离是架构核心。
  • Goal 与 Plan Mode 是模型侧的两个长时机制，均可定制。

22.1 高频问题（FAQ）

问题答案
改配置后没生效？检查是否改对了层：bundle 层的行要用 id 覆盖；确认保存触发 watcher（日志有 reload）；纯 config 变化不会重跑 apply；改 name/inject 才会换插件
行一直 PENDING？inject 的服务没就绪。看 internal/status 日志与依赖链；或服务提供了但有 check 谓词没通过（如 Loader 的 await:true）
invalid config / ValidationError？对照插件的 Config schema 修配置；--dump-config 看最终值；用 dsh plugin why 查版本
工具不在模型可见列表？插件行加载了吗（日志 apply）？register 了吗？有没有被 restrict 屏蔽？tools mode 是 code 吗（只剩 run_code）？preset 挂了对吗？
如何完全离线运行？DSH 本身是本地 Node 应用；只有模型请求与可选的遥测/搜索走网络。模型走本地端点（llm-pi-ai 配自建 provider）即可
想给插件加设置页 UI？Config schema 的元数据（description/role/default/badges…）会被 ui-settings-plugins 渲染成表单；写清楚 schema 就有 UI
可以同时跑多个 profile 吗？可以，各自进程独立（不同端口/不同任务）；共享 $DSH_HOME 的 settings 与家目录补丁层

22.2 进阶路线（学完本教程之后）

  1. 精读官方工具插件：dsh-tool-pwsh（后台任务+沙箱+escalation）、dsh-tool-subagent（委托+continuable）、dsh-tool-workflow（多 agent 编排）—— 这三个涵盖 DSH 工具的全部复杂模式。
  2. 精读 session 与投影：dsh-session、dsh-session-projection、dsh-tool-todo 的投影注册 —— 学会「事件流 → 可查询视图」范式。
  3. 读浏览器端：dsh-client-runtime、dsh-client-ui-* —— 理解双面插件与 __DSH_BOOT__ 模块表；尝试写一个 ui-* 浏览器插件。
  4. 写 Bundle 组合包：把多个插件打包成一个可分发 surface（模仿 dsh-headless 的 35 行补丁）。
  5. 给 DSH 提 PR：仓库 github.com/deepseek-ai/deepseek-harness；从修一个工具的 description 或补一个测试开始。

22.4 结语

DSH 的全部优雅之处在于：它把「配置、插件、服务、工具」统一成了同一种东西 —— 都是 Cordis 里的行与 fiber。理解了这个内核，你就同时理解了它的配置系统、插件系统、Web 表面和自定义能力。剩下的，就是多读源码、多写插件。祝你把 DSH 变成真正属于你的智能体平台。
